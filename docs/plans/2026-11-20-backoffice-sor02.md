## 1. ความต้องการ (Dept 1)

ผู้ใช้หลัก: ครูอายุมาก ใช้คอมวิทยาลัย, งานวัดผล, งานทะเบียน

Must have

- M4 แก้ไขผลการเรียนหลังอนุมัติ/ประกาศ โดยงานวัดผล ต้องใส่เหตุผล เก็บประวัติ (จาก→เป็น, ใคร, เมื่อไร)
- M5 เลื่อนชั้นทั้งกลุ่ม (ดูตัวอย่างก่อนยืนยัน) และยกเลิกการเลื่อนชั้นได้

Should have: รหัสกลุ่มเรียนบนรายงานผลการศึกษา, ปรับเกณฑ์ตัดเกรดได้, รายการวิชาที่ยังไม่ส่งผล (ไว้ตามครู)
Not now: นำเข้า Excel หลายแผ่นงาน (รอไฟล์จริง), เช็คชื่อ, รบ.1/ใบประกาศนียบัตร, สายอนุมัติหลายคน

Acceptance: ครูที่ไม่เคยใช้ทำ "กรอก→ส่ง" สำเร็จได้จากหน้าจอเอง; นักเรียนไม่เห็นเกรดก่อนประกาศ; ครูแก้วิชาคนอื่นไม่ได้แม้เรียก API ตรง; ทุกการเปลี่ยนสถานะมี audit

## 2. สถาปัตยกรรม (Dept 2)

### ข้อมูล (migration เดียว)
- `ClassGroup { id, code @unique, programId, entryYear, groupNo, yearLevel, active, advisorUserId?, createdAt }` @@unique([programId, entryYear, groupNo])
- `Student.classGroupId?` FK; คง `yearLevel`/`groupNo` ไว้ (โค้ดเดิมใช้เยอะ) แต่เขียนผ่าน service เดียวที่ sync กับกลุ่มเสมอ
- backfill: จัดกลุ่มนักเรียนเดิมตาม (programId, entryYear ?? 25xx จากรหัส 2 หลักแรก, groupNo) รหัสกลุ่มตั้งต้น = รหัสนักศึกษา 7 หลักแรก + ห้อง 2 หลัก (ตรงกับตัวอย่างจริง 68319090003 → 683190901) แก้ได้
- `CourseSection` เพิ่ม: `gradeStatus` (none|draft|submitted|returned|approved|published), `collectMax` (70), `examMax` (30), `submittedAt/By`, `returnNote`, `approvedAt/By`, `approvalDate` (date ที่ ผอ. เซ็น), `publishedAt/By`, `publishDocDate`
- `GradeRecord` เพิ่ม `collected Decimal?`, `exam Decimal?` (เกรดคำนวณจาก total หรือผลพิเศษ)
- `GradeChange { id, gradeRecordId, from, to, reason, changedById, at }`
- `AcademicTerm` เพิ่ม `gradeOpenAt?`, `gradeDueAt?`
- `PromotionBatch { id, academicYear, byId, at, undoneAt?, items Json [{classGroupId, from, to, studentIds}] }`
- `Student` เพิ่ม `graduatedAt?`, `graduationDate?`
- `AppSetting { key @id, value Json }` เก็บเกณฑ์ตัดเกรด (ค่าเริ่ม 80/75/70/65/60/55/50)

GradeRecord.status ยังเป็นตัวตัดสินว่านักเรียนเห็นหรือไม่ (published) — ประกาศ/ยกเลิกประกาศ อัปเดตทั้ง section และ records ใน transaction เดียว

### สิทธิ์ (ตรวจฝั่ง server ทุก endpoint)
- TEACHER: อ่าน/เขียนเฉพาะ section ที่ `teacherUserId = me` และสถานะ none|draft|returned, ภายในช่วงวันส่งผล (ถ้ากำหนด)
- ASSESSMENT_STAFF / ADMIN: ช่วงวันส่งผล, กระดานสถานะ, คืน/อนุมัติ/ประกาศ/ยกเลิก, แก้ไขผลพร้อมเหตุผล, เกณฑ์
- REGISTRAR / ADMIN: กลุ่มเรียน, เลื่อนชั้น, สำเร็จการศึกษา

### state machine ของ section
none → draft (ครูบันทึก) → submitted (ครูยืนยัน, ต้องครบทุกคน) → approved → published
submitted → returned (งานวัดผลคืน + เหตุผล) → draft/submitted; approved → submitted (ยกเลิกอนุมัติ); published → approved (ยกเลิกประกาศ)
ตรวจ transition ฝั่ง server ด้วย `updateMany where gradeStatus = <ที่คาดไว้>` กันกดซ้ำ/race

### logic ใน packages/shared (มี unit test)
`cutGrade(total, criteria)`, `nextSectionStatus`, `canPromote(level, yearLevel)`, `graduationCheck(planItems, grades, minCredits)`, `defaultGroupCode(studentCode, groupNo)`

### หน้าเว็บ
- เมนูบน: ครู → **กรอกเกรด** (/teach); งานวัดผล → **การเรียนและเกรด** (แท็บแรก "ส่งผลการเรียน"); งานทะเบียน → **งานทะเบียน** (กลุ่มเรียน · เลื่อนชั้น · สำเร็จการศึกษา · นักเรียน)
- /teach: การ์ดวิชาที่สอนในภาคปัจจุบัน + สถานะเป็นคำ + กำหนดส่ง; หน้ากรอก: ตารางนักเรียน ช่องเก็บ/สอบ ตัวใหญ่, Enter/↓ ไปคนถัดไป, เกรดขึ้นทันที, บันทึกอัตโนมัติ + ปุ่มบันทึก, แถบล่าง "กรอกแล้ว 28/30 · ยืนยันส่งผล"
- ปุ่มใหญ่ คำกริยาชัด ("ยืนยันส่งผลการเรียน" ไม่ใช่ "Submit"), สถานะใช้คำ + สี, ทุกการกระทำที่ย้อนไม่ได้ง่ายมี dialog ยืนยันที่บอกผล

### Threat model (สั้น)
ทรัพย์สิน: เกรด, ข้อมูลนักเรียน · ผู้โจมตี: นักเรียน (แก้เกรด), ครู (แก้วิชาคนอื่น/หลังส่ง), คนนอก · ช่องทาง: เรียก API ตรง, IDOR sectionId, race การอนุมัติ, ไฟล์ Excel ปลอม (formula/ขนาด) · ป้องกัน: ตรวจ owner+status ทุกครั้ง, transition แบบ conditional update, validate คะแนน 0..max, อ่าน Excel ด้วยค่า (ไม่รันสูตร) + จำกัดขนาด, audit ทุก transition

## v2 หลัง senior review (ใช้ฉบับนี้)

แยกรอบ: **รอบ 16 = ขั้นตอนส่งผลการเรียน** · รอบ 17 = กลุ่มเรียน + เลื่อนชั้น + สำเร็จการศึกษา (migration/backfill แยก)

การตัดสินใจหลัก
1. section เป็นเจ้าของสถานะ (`SectionGradeStatus none|draft|submitted|returned|approved|published`); `GradeRecord.status` ถูกเขียนเฉพาะในฟังก์ชันเปลี่ยนสถานะของ section ใน transaction เดียว (`recordStatusFor`)
2. คะแนนช่องเดียว "คะแนนรวม (เต็ม 100)" + เลือกผลพิเศษ; ไม่แยกเก็บ/สอบในรอบนี้
3. อัปโหลด Excel ของครู = อ่านอย่างเดียวแล้วเติมลงตาราง (ยังไม่บันทึก) ทางเขียนมีทางเดียวคือปุ่มบันทึก
4. ช่วงวันส่งผล = แจ้งเตือน/รายการส่งช้า ไม่ล็อก; ครูแก้ได้เมื่อสถานะ none|draft|returned เท่านั้น
5. การนำเข้าเกรดของหลังบ้านเดิม → "นำเข้าผลการเรียนย้อนหลัง" ห้ามทับวิชาที่ครูกำลังกรอก/ส่ง และห้ามภาคปัจจุบัน
6. เกณฑ์ตัดเกรดค่าคงที่ใน shared รอบนี้
7. ลบ POST grades/publish เดิม → ประกาศรายวิชาผ่าน state machine
8. งานวัดผลกำหนดครูผู้สอนให้วิชาที่ยังไม่มีครูได้
9. ทุกการบันทึก/เปลี่ยนสถานะ: conditional update ของ section ใน transaction (กันกดซ้ำ/บันทึกชนกับการส่ง → 409) + audit
10. ครูเรียก section ที่ไม่ใช่ของตัวเอง → 404

ไม่ทำรอบนี้: สอนร่วมหลายครู, สายอนุมัติในระบบ, เกณฑ์ปรับได้, นำเข้าหลายแผ่นงาน
